\section{Metodología}
\label{chap:metodologia}

Este capítulo describe el procedimiento experimental: tipo de estudio, métricas y orden de trabajo sobre el repositorio Ionic de referencia. La intención es que otro investigador pueda repetir las corridas con los mismos commits y comandos registrados.

\subsection{Fundamentos metodológicos según Hernández Sampieri et al.}
\label{sec:fundamentos_sampieri}
La investigación se apoya en el proceso cuantitativo descrito por \cite{sampieri2010metodologia}: delimitación de problema y objetivos, marco teórico de soporte y decisión de alcance. No hay muestra humana ni encuestas; la evidencia proviene de mediciones sobre software y tiempos de preparación de pruebas.

\subsection{Tipo de Investigación}
\label{sec:tipo_investigacion}
Es investigación \textbf{cuantitativa}, con predominio del alcance \textbf{explicativo} en formato aplicado: se construye un bridge universal extensible de simulación Capacitor, se aplica el procedimiento de cobertura y se integra una capa auxiliar basada en MCP, y se contrastan mediciones antes y después de una intervención definida. La caracterización detallada del artefacto incorpora elementos \textbf{descriptivos} dentro del mismo diseño.

\subsection{Métodos de Validación y Métricas}
\label{sec:metricas_validacion}
\begin{itemize}
    \item \textbf{Cobertura de código:} líneas y ramas según Istanbul/Jest u homólogo, siempre sobre el mismo snapshot del proyecto entre mediciones.
    \item \textbf{Tiempo de preparación de pruebas:} registro con bitácora o cronómetro (incluido el tiempo dedicado a mocks manuales eliminados o sustituidos) entre línea base y escenario con simulación integrada.
    \item \textbf{Pasaje de la suite:} número de tests que pasan en Node en cada corrida documentada.
    \item \textbf{Calidad estática opcional:} si hay Sonar configurado, puede usarse como evidencia adicional; si no existe, no se fuerza en la narrativa.
    \item \textbf{Tiempo de iteración diagnóstica:} tiempo entre recibir un reporte de cobertura/fallo y definir el siguiente escenario de prueba, comparando flujo lineal (script/CI) frente a flujo asistido por MCP.
\end{itemize}

\subsection{Diseño experimental}
\label{sec:diseno_experimental}
\begin{enumerate}
    \item \textbf{Línea base ($B$):} tomar el proyecto Ionic de referencia tal como se prueba hoy (mocks dispersos o mínimos necesarios). Anotar cobertura $C_B$, tiempo $T_B$ y estado de la suite.
    \item \textbf{Intervención ($P$):} integrar el bridge universal extensible y validarlo en el núcleo de plugins del alcance, aplicar el procedimiento de cobertura y etiquetar commits o releases para poder reproducir el estado.
    \item \textbf{Post-intervención:} medir $C_P$, $T_P$ y suite; calcular $\Delta C = C_P - C_B$ y $\Delta T = T_B - T_P$.
    \item \textbf{Comparación de orquestación:} ejecutar un subconjunto de corridas bajo dos modos equivalentes: (i) script/CI lineal y (ii) MCP asistido. Registrar tiempo de iteración diagnóstica ($T_{diag}$), número de pasos manuales y consistencia de decisiones de siguiente escenario.
    \item \textbf{Trazabilidad MCP (opcional):} conservar registros de herramientas MCP que ejecuten los mismos comandos que se usarían manualmente, para auditoría del proceso.
\end{enumerate}

\subsection{Fases de desarrollo del artefacto}
\label{sec:fases_desarrollo}
\begin{enumerate}
    \item \textbf{Ingeniería del simulador:} definir por plugin (\tcode{geolocation}, \tcode{camera}, \tcode{preferences}) qué métodos se cubren y qué perfil activa cada respuesta. Documentar el enganche en Jest o Jasmine mediante \tcode{setupFilesAfterEnv}, mocks manuales o factoría común.
    \item \textbf{Procedimiento de cobertura:} localizar usos de esos plugins; listar escenarios mínimos para ramas relevantes; escribir o ajustar tests con plantillas repetibles.
    \item \textbf{Servidor MCP auxiliar:} implementar herramientas acotadas y documentar permisos y rutas por seguridad.
    \item \textbf{Redacción de resultados:} tablas, figuras y breve discusión de amenazas (tests flaky, orden de ejecución, dependencias de red si aparecen).
\end{enumerate}

\subsection{Diseño técnico de la propuesta (Capítulo IV)}
\label{sec:diseno_tecnico_propuesta}
\subsubsection{Control determinista de asincronía y flakiness}
\label{ssec:determinismo_asincronia}
Para reducir falsos positivos y pruebas inestables, cada perfil del simulador (éxito, error, límite) se ejecutará con \textbf{control temporal determinista}. En Jest se emplearán \tcode{fake timers} (modo moderno) y avance explícito del reloj virtual con \tcode{advanceTimersByTime} y \tcode{runAllTimers}; en Jasmine se usará el reloj simulado equivalente (\tcode{jasmine.clock()}) cuando corresponda. Además, las respuestas asíncronas del simulador se encapsularán en una cola controlada de microtareas y macrotareas para evitar desfases del \textit{event loop} entre corridas. El criterio de aceptación para estabilidad será repetir lotes de pruebas en más de una corrida consecutiva sin variación de estado (sin fallas intermitentes atribuibles al orden temporal).

\subsubsection{Bridge de inyección y soporte dual Jest/Jasmine}
\label{ssec:bridge_inyeccion_dual}
El artefacto usará una factoría global de inyección para resolver en tiempo de prueba el perfil activo por plugin y exponer la misma interfaz a ambos runners. Esto permite que el proyecto cambie entre Jest/Jasmine sin reescribir los perfiles de simulación ni los escenarios de cobertura. La configuración de integración quedará versionada (archivo de setup, orden de carga y mapeo de módulos) para mantener reproducibilidad.

\subsubsection{Mock por defecto para plugins fuera de alcance}
\label{ssec:fallback_mock}
Si durante la ejecución aparece un plugin Capacitor no mapeado explícitamente en el núcleo (\tcode{geolocation}, \tcode{camera}, \tcode{preferences}), el sistema aplicará un \textbf{mecanismo de caída segura}: generación dinámica de un mock por defecto mediante \tcode{Proxy} de JavaScript, con respuestas asíncronas genéricas y trazadas en log. Este fallback evita que la suite se detenga por razones técnicas ajenas al alcance y permite etiquetar esos casos como ``pendientes de implementación específica'' en lugar de romper la validación principal.

\subsubsection{Justificación operativa de MCP frente a automatización clásica}
\label{ssec:justificacion_mcp_operativa}
El uso de MCP no se limita a ejecutar comandos que también podría correr un script. La diferencia propuesta es \textbf{orquestación semántica}: un agente puede leer el estado del reporte de cobertura (líneas/ramas faltantes, suites fallidas, tipo de error) y seleccionar de forma guiada el siguiente perfil de simulación a probar (éxito, error, límites) antes de la siguiente corrida. En ese contexto, MCP aporta un protocolo de contexto entre herramientas y agente, mientras que Bash/CI aporta solo secuencias fijas. Para no dejar esta afirmación en nivel declarativo, la tesis incluye una comparación explícita con flujo lineal, usando $T_{diag}$ y pasos manuales como indicadores observables.

\subsection{Instrumentos y fuentes bibliográficas iniciales}
\label{sec:instrumentos_biblio}
Para contrastar decisiones de diseño y métricas se usan principalmente \cite{nie2023gui_mobile_mapping,schafer2024testpilot,olsthoorn2024syntest_javascript}; para MCP, \cite{mcp-spec2025}.

\subsubsection{Población y muestra (si aplica)}
\label{sec:poblacion_muestra}
Este plan no trabaja con participantes humanos ni encuestas como fuente principal de evidencia. La unidad de análisis es el \textbf{proyecto Ionic de referencia} y sus artefactos de prueba (suite, cobertura y tiempos). Si durante la ejecución se incorpora evaluación con desarrolladores o usuarios, se añadirá la delimitación de población, criterio muestral e instrumento correspondiente.

La validación busca evidencia bajo condiciones declaradas de que el artefacto cumple el objetivo general (mejora medible de cobertura y menor fricción en preparación de pruebas en Node), sin presentar corridas en dispositivo como equivalentes a las unitarias con simulación.
